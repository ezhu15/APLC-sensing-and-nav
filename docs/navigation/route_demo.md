# Route Server demo (simulation, simulated Quest)

Package: `src/aplc_navigation`. Answers two questions about predefined-route navigation:

1. **Does the robot detect obstacles in real time?** Obstacles come only from a depth
   camera at headset height, feeding Nav2's costmaps live; nothing about them is in any map.
2. **Is route following rigid vertex-to-vertex driving?** No. The Route Server turns the
   graph into a path, and the MPPI controller follows it loosely: it leaves the path to
   pass an obstacle beside the lane, and when a lane is blocked the Route Server picks
   another lane.

The Meta Quest is not needed: `fake_quest` publishes what `aplc_scene_ros`'s
`quest_bridge` would, from Gazebo's ground truth plus a Quest-like error model.

## Run it

```bash
cd ~/APLC-sensing-and-nav
colcon build --symlink-install && source install/setup.bash
export DISPLAY=:0 XAUTHORITY=$(ls /run/user/$(id -u)/.mutter-Xwaylandauth.* | head -1)

ros2 launch aplc_navigation route_demo.launch.py        # Gazebo + RViz; robot on the landing
ros2 run aplc_navigation route_demo --goal trunk        # second terminal: drive the route
ros2 run aplc_navigation route_demo --goal landing      # and back up the ramp
```

Obstacles (any time, from another terminal; positions in the map frame = Gazebo world):

```bash
ros2 run aplc_navigation obstacles box --y -2.3   # box beside lane A's centerline: drives around it
ros2 run aplc_navigation obstacles box            # box dead-center on lane A
ros2 run aplc_navigation obstacles block --lane a # wall across lane A: reroute through lane B
ros2 run aplc_navigation obstacles walker         # person pacing across the driveway (Ctrl+C ends)
ros2 run aplc_navigation obstacles clear
```

Faster checks: start on the apron with `x:=1.4 y:=-3.4 z:=0.05 yaw:=0`, and run headless
with `gui:=false rviz:=false`. Other launch arguments: `headset_height` (1.0 m),
`headset_pitch` (0.6 rad down), `quest_noise`, `quest_drift_max`, `quest_dropout_period`,
`camera_width/height/rate` (424 x 240 at 15 Hz), `seed`.

`route_demo` prints the route as graph node names, `REROUTE` when it changes, and a
summary scored against Gazebo's true pose (time, reroutes, largest distance from the route
path, localization error, final error). `--csv FILE` saves the true and estimated track.

In RViz: route graph (markers), the path the controller follows (cyan), MPPI's chosen
trajectory (yellow), local and global costmaps, the headset's point cloud and the Quest pose.

## How it fits together

```
Gazebo ── /ground_truth/odom ──> fake_quest ── /quest/pose, TF map -> odom
   │                                  ^
   ├─ wheels, IMU ──> EKF ── /odometry/filtered, TF odom -> base_footprint
   └─ depth camera (headset mount) ──> /camera/camera/depth/color/points
                                           │
                               local + global costmaps (voxel layer)
                                           │
bt_navigator (behavior_trees/navigate_on_route.xml)
   1. ComputeRoute  -> route_server: graph path from robot to goal, skipping edges the
                       global costmap marks blocked (CostmapScorer)
   2. FollowPath    -> controller_server (MPPI) -> /diff_drive_controller/cmd_vel
   3. on failure: wait 3 s, go to 1 (the new route avoids the blocked lane)
```

- **Route graph** `graphs/house_route.geojson`, generated by `scripts/gen_route_graph.py`
  (edit the node list there, regenerate with `-o house_route.geojson`, never hand-edit):
  inside → landing → ramp top → ramp bottom → apron → lane A or lane B → trunk.
  Lane A is 0.26 m shorter, so it is the default.
- **fake_quest** error model: 4 mm and 0.23° white noise, a random-walk drift up to 10 cm
  and 2° that is mostly removed every 20 s (an anchor re-alignment, seen as a small jump),
  optional tracking loss. It publishes `/quest/pose`, `/quest/status` (same JSON key as
  `quest_bridge`), `map -> quest_world -> quest_headset`, and `map -> odom`, so the EKF's
  drift is corrected the same way AMCL or SLAM would correct it.
- **Headset camera**: the existing RealSense model moved to the headset mount (0.15 m
  forward, 1.0 m above the ground, tilted 0.6 rad down).
- **Rerouting** happens when the controller cannot make progress (0.3 m in 12 s) and the
  new route is computed once per attempt, not continuously, so an obstacle the robot can
  pass does not trigger a reroute. Nav2 also offers `ComputeAndTrackRoute` (continuous
  tracking with route operations); this demo does not use it.

## Results (headless, seed 7, 17 to 18 November 2026)

| Scenario | Start | Result | Time (sim) | Reroutes | Largest distance from route |
| --- | --- | --- | --- | --- | --- |
| No obstacles, Quest tracking lost 1 s in every 8 s | landing | reached trunk | 59 s | 0 | 0.8 m (swing at the apron turn) |
| Box beside lane A (y −2.3) | landing | reached trunk | 37 s | 0 | 0.8 m (same turn) |
| Box beside lane A (y −2.3) | apron | reached trunk | 14 s | 0 | 0.34 m |
| Walker crossing lane A | apron | reached trunk, paused ~2 s | 19 s | 0 | 0.33 m |
| Wall across lane A | apron | reached trunk via lane B | 63 s | 1 | 0.7 m |
| Box dead-center on lane A | apron | reached trunk via lane B | 62 s | 1 | 0.7 m |

Localization error (Quest + EKF against ground truth): mean 1.5 to 2 cm, max under 8 cm;
11 cm with the tracking losses (the EKF carries the robot through each 1 s gap).
The largest distances from the route are at the apron, where MPPI swings wide through the
sharp turn from the ramp bottom toward the lane, not at the obstacles.
Final error at the trunk: 0.22 to 0.25 m (the goal checker's tolerance is 0.25 m).

## Known limitations

- **Box dead-center on the path**: MPPI stops in front of it instead of picking a side
  (left and right cost the same, and their average is straight ahead). The robot still
  arrives, through the behavior tree's reroute, but it takes a 12 s stall to get there.
  A box off-center by 0.3 m is passed without stopping.
- **Ramp and the 2D EKF**: the EKF has no pitch, so at the top and bottom of the ramp the
  flat ground ahead appears raised by up to 0.18 m at 2.2 m. The costmaps therefore ignore
  points below 0.30 m and beyond 2.2 m: obstacles lower than 30 cm are not seen. A 3D EKF
  or a pitch-corrected cloud would remove this limit.
- **Local costmap in the map frame**, not odom: the odom frame turns with the gyro bias, and
  remembered obstacles smeared into a wedge that closed the ramp. The Quest's map frame does
  not drift. The demo also uses a 0.1°/s gyro bias (calibrated) instead of
  `world.launch.py`'s 1°/s default.
- **Ramp clearance** is tight (1.2 m wide, robot 0.54 m), so MPPI checks a circle rather
  than the full footprint; a footprint check made it creep at 1 cm/s.
- **CPU**: tuned for the 4-core VM (MPPI at 10 Hz, 800 samples; camera 424 x 240 at 15 Hz;
  `/wheel_encoders` off). Nav2's lifecycle heartbeat is off (`bond_timeout:=0`) because the
  controller can stall more than 10 s under full load.
- Scripts installed with `RENAME` in CMake (`fake_quest`, `obstacles`, `route_demo`, and
  `aplc_gazebo`'s scripts) are **copied, not symlinked**, even with `--symlink-install`:
  rebuild after editing them.
